## 模块 1 · 规则知识库（`core/rules`）

> 对应文件：[PermissionRules.kt](../app/src/main/java/com/ice/guard/core/rules/PermissionRules.kt)、[Finding.kt](../app/src/main/java/com/ice/guard/core/rules/Finding.kt)

### 设计思想

单一高危权限不足以判定一个应用有问题——很多正常应用也要存储权限。真正有判别力的是
**权限组合**：例如「读取短信 + 联网」意味着可以把短信外传，而「短信 + 联网 + 无障碍」
则意味着可以静默读取验证码并代你点击确认按钮，这是国内手机木马最典型的敛财路径。

### 1.1 单权限权重表 `PERMISSION_WEIGHTS`

`Map<String, Int>`，按敏感度分三级：

| 级别 | 代表权限 | 权重区间 |
|---|---|---|
| 一级：可直接造成资金 / 隐私损失 | `BIND_ACCESSIBILITY_SERVICE`(90)、`BIND_DEVICE_ADMIN`(90)、`REQUEST_INSTALL_PACKAGES`(80)、`READ_SMS`(80)、`RECEIVE_SMS`(80)、`PROCESS_OUTGOING_CALLS`(70)、`READ_CALL_LOG`(70)、`SYSTEM_ALERT_WINDOW`(65)、`CALL_PHONE`(60)、`WRITE_SETTINGS`(60) | 60–90 |
| 二级：隐私数据读取 | `READ_CONTACTS`(55)、`RECORD_AUDIO`(55)、`ACCESS_BACKGROUND_LOCATION`(60)、`CAMERA`(50)、`ACCESS_FINE_LOCATION`(45)、`READ_PHONE_STATE`(45)、`READ_EXTERNAL_STORAGE`(35) 等 | 30–60 |
| 三级：一般能力 | `INTERNET`(10)、`FOREGROUND_SERVICE`(10)、`ACCESS_NETWORK_STATE`(5)、`WAKE_LOCK`(5)、`POST_NOTIFICATIONS`(5)、`VIBRATE`(3) | 3–10 |

### 1.2 组合规则表 `COMBO_RULES`（18 条，核心判别力所在）

| id | 组合条件 | 加成 | 等级 |
|---|---|---|---|
| `combo.sms_net` | 读取短信 + 联网 | +45 | CRITICAL |
| `combo.sms_net_a11y` | 接收短信 + 联网 + 无障碍 | +60 | CRITICAL |
| `combo.a11y_net` | 无障碍 + 联网 | +40 | CRITICAL |
| `combo.install_overlay` | 安装应用 + 悬浮窗 | +45 | HIGH |
| `combo.admin_overlay` | 设备管理器 + 悬浮窗 | +45 | HIGH |
| `combo.bgloc_net` | 后台定位 + 联网 | +35 | HIGH |
| `combo.contacts_net` | 通讯录 + 联网 | +30 | MEDIUM |
| `combo.mic_cam_net` | 麦克风 + 摄像头 + 联网 | +40 | HIGH |
| `combo.store_install` | 存储写入 + 安装应用 | +25 | MEDIUM |

1.1.0 扩充的 9 条，覆盖两类此前遗漏的场景——「**无联网也能作案**」
（全程本地完成盗刷，不留传输痕迹）与「**下载 → 投放 → 安装**」链条：

| id | 组合条件 | 加成 | 等级 |
|---|---|---|---|
| `combo.sms_a11y` | 读取短信 + 无障碍 | +50 | CRITICAL |
| `combo.sms_recv_a11y` | 接收短信 + 无障碍 | +50 | CRITICAL |
| `combo.call_net` | 通话记录 + 联网 | +35 | HIGH |
| `combo.call_out` | 拨号 + 通话记录 + 联网 | +45 | HIGH |
| `combo.overlay_net` | 悬浮窗 + 联网 | +35 | HIGH |
| `combo.install_net` | 联网 + 安装应用 | +40 | HIGH |
| `combo.admin_install` | 设备管理器 + 安装应用 | +50 | CRITICAL |
| `combo.profile_net` | 通讯录 + 短信 + 通话记录 + 联网 | +55 | CRITICAL |
| `combo.spy_local` | 录音 + 摄像头 + 后台定位 | +45 | HIGH |

每条规则都带 `reason` 字段（判定理由的人类可读说明），并随发现项一并展示——
用户看到的不是黑箱分数，而是"为什么这么判"。

### 1.3 评分算法 `scoreOf()`

```
raw = 单权限最高分 + (命中组合加成之和 × 0.6)
score = raw 压缩到 [0, 100]
```

**为什么用「最高单项 + 组合加成」而非简单求和？**
避免权限数量多的正常应用被误判为高危——一个社交应用有十几个普通权限，
简单求和会直接顶满 100，而取最高分 + 组合加成则不会。

### 1.4 风险等级 `RiskLevel`

按数值升序，便于比较与排序；`fromScore()` 按阈值反查：

| 等级 | 分值区间 | label |
|---|---|---|
| `SAFE` | 0–14 | 安全 |
| `LOW` | 15–39 | 低风险 |
| `MEDIUM` | 40–64 | 中风险 |
| `HIGH` | 65–84 | 高风险 |
| `CRITICAL` | 85–100 | 极高风险 |

### 1.5 发现项 `Finding`

报告的最小单元，字段：`id / title / detail / level / weight / category`。
`Category` 枚举：`PERMISSION`（权限）/ `APK`（安装包）/ `ENVIRONMENT`（环境）/
`NETWORK`（网络）/ `STORAGE`（存储）。

## 模块 2 · 应用权限审计（`PermissionAuditEngine`）

> 对应文件：[PermissionAuditEngine.kt](../app/src/main/java/com/ice/guard/core/scanner/PermissionAuditEngine.kt)

### 工作流程

1. 用 `PackageManager.getInstalledPackages(GET_PERMISSIONS)` 枚举全部包。
2. 过滤掉自身包名；`includeSystem=false` 时再过滤掉系统应用（避免噪音）。
3. 对每个包读取 `requestedPermissions` → `PermissionRules.scoreOf()` 评分。
4. 生成发现项 `buildFindings()`：
   - 权重 ≥ 60 的高危单权限逐条列出；
   - 命中的组合规则逐条列出（这是判别力核心）。
5. 按分数降序返回。

### 关键健壮性设计

- `safeAudit()` 用 `try/catch` 包裹单个应用的审计——**单个应用解析失败不中断整轮扫描**。
- `readablePermission()` 将权限名映射为中文可读名（如
  `BIND_ACCESSIBILITY_SERVICE` → "无障碍服务（模拟操作）"），未收录的退回短名。

### 能力边界（诚实声明）

- 只读取「应用声明的权限」与「是否授予」，不监控运行时行为，无法判断权限是否被滥用。
- 风险分为启发式评估，不等同于「该应用是恶意的」这一结论。

## 模块 3 · 安装包静态扫描（`ApkScanEngine` + `AxmlParser`）

> 对应文件：[ApkScanEngine.kt](../app/src/main/java/com/ice/guard/core/scanner/ApkScanEngine.kt)、[AxmlParser.kt](../app/src/main/java/com/ice/guard/core/scanner/AxmlParser.kt)

### 3.1 `ApkScanEngine` 工作流程

1. 从 `Download` 及外部根目录递归查找 `.apk`（**深度 3 层，单次最多 200 个文件**，防止耗时失控）。
2. 用自研 `AxmlParser` 读出其声明的权限与四类组件（不解压全部内容）。
3. 复用 `PermissionRules` 组合规则评估风险；组件交给 `ComponentAnalyzer` 评估暴露面。
4. 计算 SHA-256（流式读取 8KB 缓冲，避免载入大文件）便于用户核对。
5. 只对**中风险及以上**的 APK 生成发现项。

### 3.2 自研 AXML 解析器（重点）

APK 内的 `AndroidManifest.xml` 是编译后的二进制格式（chunk-based），无法当作文本读取。
本项目**没有引入 apk-parser 等第三方库**，而是按 AOSP 定义的格式手写解析器。

**目标明确**：只提取三类信息，不做完整 DOM 还原——
`<manifest>` 的 `package` 属性、`<uses-permission>` 的 `android:name` 属性，
以及四类组件（`activity` / `service` / `receiver` / `provider`）的 `android:name`、
`android:exported`、`android:permission` 与其 `intent-filter` 下的 `action`。

#### 格式要点（来自 AOSP resource 定义）

```
Header:      ResChunk_header { type(u16), headerSize(u16), size(u32) }
StringPool:  type=0x0001，含字符串偏移表与字符串数据
StartTag:    type=0x0102，含属性列表
Attribute:   { ns(u32), name(u32), rawValue(u32), typedValue(Res_value) }
             Res_value: size(u16) res0(u8) dataType(u8) data(u32)
             → dataType 位于属性块起始偏移 +15 处
```

#### 实现要点与踩坑记录

- **字符串池编码**：需按 `flags & 0x100` 区分 **UTF-8 与 UTF-16** 两条解码路径
  （实测 AAPT2 输出为 UTF-16，不能假定 UTF-8）。
  - UTF-8：`[u16变长长度][u8变长字节长度][字节数据]`，解码以字节长度为准。
  - UTF-16：`[u16长度][UTF-16LE 字符数据]`，长度最高位为 1 时表示两段 u16 表示的大长度。
- **属性区偏移**：`attributeStart` 位于 node 起始的 `+8`、`attributeCount` 位于 `+12`；
  属性区起始 = node 起始 + `attributeStart`（**是相对 node 起始的偏移，不要再叠加 header 大小**）。
- **命名空间属性回退**：命名空间属性的 `name` 索引可能指向字符串池中的空串，
  此时以 namespace URI 的最后一段（如 `android`）作为属性名回退，避免丢失信息。
- **防御性解析**：所有越界访问均有防护（`if (base + ATTR_SIZE > buf.capacity()) break`），
  单个属性解析失败不影响整体；非法的 `chunkSize` 直接 `break` 避免死循环。
- **不抛异常**：解析异常统一转为 `success=false` 的返回值。

#### 正确性验证

解析器由**真实样本**验证：测试夹具 `real_manifest.axml` 是 AAPT2 编译本工程产生的
二进制清单（17940 字节，含 25+ 个组件），期望值取自 `aapt2 dump xmltree` 输出——
测试会逐一断言四类组件均被解析出来，而不是只看权限列表。

### 3.3 组件级分析（`ComponentAnalyzer`）

权限之外的高价值判定维度是**组件暴露面**，回答的是"攻击面有多大"：

- `exported=true` 且无 `android:permission` 保护的组件，意味着**任意应用**都能唤起它。
  按类型汇总为发现项：Provider（55）/ Service（30）/ Receiver（25）/ Activity（25）；
- **高敏感绑定服务识别**：应用在组件上声明 `BIND_*` 权限，等于对外宣告"我实现了
  无障碍 / 通知读取 / VPN / 输入法 / 设备管理器 / 通话筛查服务"（权重 45–70）。
  这比权限声明更有信息量——声明无障碍权限不算罕见，**真的实现了无障碍服务**才值得注意；
- 精度控制（避免噪音淹没用户）：启动器入口与有权限门槛的组件不计入"对外暴露"；
  Provider 的读/写权限是分开声明的，**只有读写都被保护才算有门槛**。

### 3.4 安装来源与签名（`SignatureInspector`）

回答"应用是谁、从哪来"：

- 识别侧载（系统未记录安装来源，或来源不在 12 个已知商店清单内，权重 35）、
  `debuggable`（45）、`testOnly`（25）；
- 给出签名证书 SHA-256（API 28+ 用 `GET_SIGNING_CERTIFICATES`，低版本回退
  `GET_SIGNATURES`），供用户自行核对。

**不做签名黑名单比对**——那需要联网与样本库，与本项目的本地化原则冲突；
给出的 SHA-256 是供核对的原始事实，不是结论。

### 能力边界

- 不含病毒特征库，无法判定「这个 APK 是某个已知病毒」。
- 评估依据是权限的静态特征，属于启发式提示。
- 不联网、不上传任何文件。

## 模块 4 · 设备环境检测（`EnvironmentCheckEngine`）

> 对应文件：[EnvironmentCheckEngine.kt](../app/src/main/java/com/ice/guard/core/scanner/EnvironmentCheckEngine.kt)

`check()` 依次执行 7 项探测，返回按权重降序的 `List<Finding>`：

| 检测项 | 方法 | 信号来源 | 风险权重 |
|---|---|---|---|
| **Root 痕迹** | `checkRoot()` | 4 策略交叉 | 命中 ≥2 项 → HIGH/70；1 项 → MEDIUM/40 |
| **USB 调试** | `checkDeveloperOptions()` | `Settings.Global.ADB_ENABLED` | MEDIUM/45 |
| **模拟位置** | `checkDeveloperOptions()` | `Settings.Secure.ALLOW_MOCK_LOCATION` | LOW/25 |
| **无障碍服务** | `checkAccessibilityServices()` | `Settings.Secure.ENABLED_ACCESSIBILITY_SERVICES` | ≥3 个 → HIGH/65；否则 MEDIUM/45 |
| **设备管理器** | `checkDeviceAdmins()` | `DevicePolicyManager.activeAdmins` | MEDIUM/50 |
| **未知来源安装** | `checkUnknownSources()` | `Settings.Secure.INSTALL_NON_MARKET_APPS` | MEDIUM/45 |
| **存储加密** | `checkStorageEncryption()` | `DevicePolicyManager.storageEncryptionStatus` | MEDIUM/40 |
| **锁屏强度** | `checkScreenLock()` | `KeyguardManager.isDeviceSecure` | HIGH/60 |

### Root 检测的多策略交叉

任何单一特征都可能误报，因此用 4 条策略交叉取证，按命中数量给出置信度：

1. **常见 su 二进制路径**（10 个路径，如 `/system/bin/su`、`/magisk/.core/bin/su`）。
2. **build 标签**：`Build.TAGS` 含 `test-keys`（工程机特征）。
3. **Root 管理应用**：Magisk、SuperSU、KernelSU 等 6 个包名。
4. **可写系统目录**：`/system`、`/system/bin`、`/system/xbin` 是否可写。

命中 1 项标注"置信度较低（可能为误报）"，2 项"中等"，≥3 项"较高"。

### 能力边界

- Root 检测为启发式判断，无法 100% 确证，存在误报与漏报。
- 「检测到 Root」本身不等于「设备不安全」，而是提示风险面扩大。

## 模块 5 · 体检编排（`HealthCheckCoordinator`）

> 对应文件：[HealthCheckCoordinator.kt](../app/src/main/java/com/ice/guard/core/scanner/HealthCheckCoordinator.kt)

### 职责

在 `Dispatchers.IO` 上串行调度各模块，通过 `onProgress` 回调向 UI 报告进度，
汇总为一份 `ScanReport`。

### 评分模型（自研）

```
模块得分 = 100 - (该模块发现项权重之和 / 10)，单模块扣分上限 40
综合得分 = Σ(模块权重 × 模块得分) / Σ模块权重
```

模块权重：**权限审计 50% / 环境检测 30% / APK 扫描 20%**。
若某模块未执行（如 `includeApk=false`），其权重按比例分摊到其余模块。

**为什么单模块扣分上限 40？**
避免单一模块的密集告警把总分一次性压到底，导致评分失去区分度。

## 模块 6 · 报告与历史（`ScanReport` + `ScanHistoryStore`）

> 对应文件：[ScanReport.kt](../app/src/main/java/com/ice/guard/core/report/ScanReport.kt)、[ScanHistoryStore.kt](../app/src/main/java/com/ice/guard/data/ScanHistoryStore.kt)

### `ScanReport`

- 结构：`timestamp / overallScore / modules[]`，每个 `ModuleResult` 含
  `moduleId / moduleName / score / findings[]`。
- 派生属性：`level`（由 overallScore 反查）、`allFindings`（全局发现项按权重降序）。
- 序列化：**手写 JSON**（用平台自带 `org.json`，不引入 Gson / Moshi）：
  - `toJson()` → 缩进 2 空格的 JSON 字符串；
  - `toMarkdown()` → 带标题、评分、分模块明细与免责声明的 Markdown。

### `ScanHistoryStore`

自研轻量实现，使用 `SharedPreferences`（`ice_guard_history`）+ 手写 JSON，
**上限 50 条**，超出自动裁剪：

- `save(report)`：追加到队首，超限裁剪；
- `loadRaw()` / `recent(n)`：读取全部 / 最近 n 条；
- `clear()`：清空；
- `scoreDelta(current)`：与上一次体检对比的分数差。

**设计取舍**：历史记录结构简单、条目有限，无需引入数据库。解析采用 `optXxx` 与
`runCatching`，任何损坏条目都会被跳过而非崩溃。

### 报告导出（`ReportExporter`，位于 `ui/home`）

将 Markdown / JSON 写入应用私有目录 `filesDir/reports`，再经 `FileProvider` 分享：

- **不使用外部存储写入权限**，改用 FileProvider 授权分享，遵循最小权限原则。
- `exportAndShare()` 只分享 Markdown，`exportToFiles()` 仅落盘返回文件路径列表。

## 模块 7 · 新装应用监听与告警（`core/monitor`）

> 对应文件：[InstallMonitor.kt](../app/src/main/java/com/ice/guard/core/monitor/InstallMonitor.kt)、[InstallMonitorReceiver.kt](../app/src/main/java/com/ice/guard/core/monitor/InstallMonitorReceiver.kt)

### 工作方式

- **这是本应用能做到的「最接近拦截」的合法形态**：监听系统 `ACTION_PACKAGE_ADDED`
  广播——**不需要任何特殊权限**。
- `InstallMonitorReceiver.onReceive()` 的过滤逻辑：
  - 只处理 `ACTION_PACKAGE_ADDED`；
  - `EXTRA_REPLACING=true`（更新安装）时**跳过**，避免用户每次升级都收到提醒；
  - 跳过自身包名。
- 重活（解析权限、算分）放在 `goAsync()` 的背景线程里做，不阻塞主线程；
  广播链路**不抛出**，任何异常只记录，不影响系统。
- `InstallMonitor`：
  - `ALERT_THRESHOLD = 65`（分数达到即告警，锁定在高级风险区间下界）；
  - `audit()` 用 `runCatching` 包裹，异常返回 `null`；
  - `notifyIfNeeded()` 用本地通知（channel `ice_guard_install_monitor`），
    未授予通知权限时静默失败，不影响主流程。

### 边界（诚实声明）

- 广播是**安装完成后**才收到的，所以这是「**装后告警**」，不是「安装前拦截」。
  系统没有给第三方应用「阻止安装」的 API，Android 14+ 更收紧了这一口子。
- 若用户已授权 Shizuku，可在审计页一键停用或卸载——这是「事后处置」。

## 模块 8 · 权限处置（可选，`core/privilege`）

> 对应文件：[ShizukuBridge.kt](../app/src/main/java/com/ice/guard/core/privilege/ShizukuBridge.kt)、[ShellExecutor.kt](../app/src/main/java/com/ice/guard/core/privilege/ShellExecutor.kt)、[UserService.kt](../app/src/main/java/com/ice/guard/core/privilege/UserService.kt)、[DisposalEngine.kt](../app/src/main/java/com/ice/guard/core/privilege/DisposalEngine.kt)

### 8.1 为什么必须用户手动配对

Shizuku 要以 shell 身份启动一个服务进程，而"以 shell 身份启动"这一步必须由用户完成：
要么在电脑上跑一次 `adb shell sh .../start.sh`，要么用 Android 11+ 的**无线调试配对**。

**这一步没法由 App 代劳**——把 Shizuku 的代码打进本 APK，它启动时依然是普通应用的 uid，
起不来服务。集成度再高也不能凭空获得 shell 权限。这是权限模型的硬约束，不是实现选择。

### 8.2 四层调用链

```
ShizukuBridge（状态查询 + 授权请求，不含处置逻辑）
      │  State: NOT_INSTALLED / SERVICE_NOT_RUNNING / PERMISSION_REQUIRED / GRANTED
      ▼
ShellExecutor（命令执行器，双通道）
      │  通道1 Shizuku：把命令交给 shell(uid 2000)/root 身份的 UserService 执行
      │  通道2 本地：Runtime.exec，能力等同本应用自身权限（仅只读查询用）
      ▼
UserService（IUserService.Stub 实现，运行在 Shizuku 服务进程中）
      │  exec(command) → [exitCode, stdout, stderr]
      ▼
DisposalEngine（处置语义：DISABLE / ENABLE / UNINSTALL / CLEAR_DATA）
```

### 8.3 各组件要点

- **`ShizukuBridge`**（object）：只做"状态查询 + 授权请求"。
  - `register()` 注册授权结果与 Binder 死亡监听（在 `IceGuardApp.onCreate` 调用）。
  - `state()` 用命令式检查（`pingBinder` → `checkSelfPermission`）返回四态枚举，
    **用枚举而不是多个 boolean**，避免出现"看似可用实则未授权"的中间态。
  - 所有方法用 `runCatching` 包裹，不会抛异常。
- **`ShellExecutor`**：
  - `serviceArgs` 中 **tag 必须固定**（`"IceGuardShellService@1"`），因为类名会被 R8 混淆，
    Shizuku 靠 tag 判断"是否同一个服务"。
  - `bindService()` 做有上限的等待（`CountDownLatch` + 8s 超时）。
  - `exec()` 优先走 Shizuku 通道，服务不可用时回退本地通道。
  - **命令以数组传入，不做字符串拼接**，避免命令注入。
- **`UserService`**：`IUserService.Stub` 实现，两个构造器均标注 `@Keep`（反射实例化）。
  `exec()` 返回 `[exitCode, stdout, stderr]` 三元组，命令超时（15s）编码为 `-2`，不抛异常。
- **`ShellResult`**：永远不抛异常；`ok` 仅由 `exitCode == 0` 判定。

### 8.4 处置动作与真实效果

| 动作 | 命令 | 效果 | destructive |
|---|---|---|---|
| `DISABLE` | `pm disable-user --user 0 <pkg>` | 冻结应用，图标消失、无法运行，可恢复 | 否 |
| `ENABLE` | `pm enable <pkg>` | 恢复被停用的应用 | 否 |
| `UNINSTALL` | `pm uninstall --user 0 <pkg>` | 卸载（仅当前用户） | **是** |
| `CLEAR_DATA` | `pm clear <pkg>` | 抹除应用数据，保留本体 | **是** |
| 撤销权限 | `pm revoke <pkg> <perm>` | 收回指定运行时权限 | — |
| 列表确认 | `pm list packages -d` | 核对停用状态 | — |

UI 侧不提供「一键清理全部」——批量破坏性操作风险过高，必须逐个确认，
破坏性动作标红二次确认；处置后刷新列表，让"是否真的生效"体现在数据上。

### 8.5 做不到什么（诚实声明）

- 拿到的是 shell（uid 2000）权限，不是 uid 0。
- **看不到、也杀不掉别的应用进程**，即使有 shell 权限 `kill` 也只是让进程重启，
  且无法读取其内存与实时行为。因此本引擎没有"实时拦截病毒进程"这一项。

## 模块 9 · 安全守护（`core/guard`）

> 对应文件：[AutoResponder.kt](../app/src/main/java/com/ice/guard/core/guard/AutoResponder.kt)、
> [GuardModels.kt](../app/src/main/java/com/ice/guard/core/guard/GuardModels.kt)、
> [GuardService.kt](../app/src/main/java/com/ice/guard/core/guard/GuardService.kt)、
> [GuardAccessibilityService.kt](../app/src/main/java/com/ice/guard/core/guard/GuardAccessibilityService.kt)、
> [GuardSweep.kt](../app/src/main/java/com/ice/guard/core/guard/GuardSweep.kt)、
> [ForegroundAppWatcher.kt](../app/src/main/java/com/ice/guard/core/guard/ForegroundAppWatcher.kt)、
> [WatchdogWorker.kt](../app/src/main/java/com/ice/guard/core/guard/WatchdogWorker.kt)

把"检测"与"处置"串成一条自动化链路：**事件一到就判定，判定通过就终止**。

### 9.1 四条检测通道 + 一条统一响应管线

| 通道 | 触发时机 | 载体 | 特殊权限 |
|---|---|---|---|
| 1 · 安装 / 更新 | `PACKAGE_ADDED` · `PACKAGE_REPLACED` | `InstallMonitorReceiver` | 无 |
| 2 · 开机自检 | `BOOT_COMPLETED` | `BootGuardReceiver` | 无 |
| 3 · 前台唤醒 | 前台应用切换（轮询，约 1 秒） | `GuardService` + `ForegroundAppWatcher` | 需「使用情况访问」 |
| 4 · 无障碍前台事件 | 窗口状态变化 | `GuardAccessibilityService` | 需手动开启无障碍服务 |
| 兜底 · 周期巡检 | WorkManager，最小间隔 15 分钟 | `WatchdogWorker` | 无 |

四条通道全部汇入 `AutoResponder` 这一条管线，不存在"某个通道单独处置"的旁路。

### 9.2 `AutoResponder`：决策与处置

```
取分（10 分钟缓存）→ 读策略 → 决策 →（可选）终止 → 落日志 → 发通知
```

**决策优先级**（`decide()` 是纯函数，可被单元测试完整覆盖）：

1. 评分未达阈值 → `IGNORE`，**不写日志**（避免把日志变成流水账）；
2. 达到阈值但未开自动处置 / 未授权 Shizuku → `ALERT_ONLY`（默认行为）；
3. 达到阈值且允许自动处置 → `TERMINATE_ONLY` / `TERMINATE_AND_FREEZE`，
   `am force-stop` 立即结束其全部进程，按策略追加 `pm disable-user` 冻结；
4. 用户主动触发（通知按钮 / 守护中心）→ `forced=true`，不受阈值与开关限制，
   但仍需 Shizuku 授权才能真正生效。

判定结果落成 `GuardEvent`（通道 / 结论 / 动作 / 命令返回 / 耗时），写入本地拦截日志
（上限 200 条），并触发通知——未真正处置且具备终止能力时，通知带「立即终止」按钮，
点击即可完成一次手动处置。

### 9.3 秒级终止的实现与边界

- `DisposalEngine.terminate()` 先执行 `am force-stop`，按策略再执行 `pm disable-user`，
  返回逐条 `ShellResult`；
- `GuardEvent.detail` 记录**实际耗时与命令返回**（如"耗时 412ms；am force-stop…"），
  `viaShizuku` 标注是否经 shell 权限执行——处置是否真的生效可在设备上核验；
- **瓶颈在检测，不在终止**：Android 沙箱隔离了应用间观测，第三方应用看不到别的应用
  的行为、内存与日志。本项目给的是**事件驱动的秒级响应**，不是"实时行为监控"。

### 9.4 性能设计：缓存与节流

前台通道每次窗口切换都会走管线，因此：

- **体检结果 10 分钟缓存**（上限 300 条，过期清理），避免反复查询 PackageManager；
- **处置 30 秒节流**（按包名），避免同一应用被反复处置刷爆日志；
- 安装 / 更新后调用 `invalidate()` 让缓存分数立即失效——新装应用的分数不能沿用旧值。

### 9.5 `GuardSweep`：巡检与状态漂移检测

开机自检与周期巡检共用同一段逻辑，做两件事：

1. **全盘复检**：枚举已安装应用，对达到阈值的逐个走 `AutoResponder`；
2. **状态漂移检测**：复查"曾被终止并冻结的应用是否又回到可运行状态"——
   被手动启用、被其他应用拉活、系统更新后还原，都会在这里被发现并重新告警。
   **单次处置不是终点**，这是巡检真正的价值。

宁可漏报也不误报：查询失败（`disabledPackagesOrNull()` 返回 `null`）或列表为空时
不做任何结论，避免用户收到"某应用复活了"的假警报。

### 9.6 无障碍通道的自我限制

守护通道 4 使用无障碍服务，但只用了它能力的**最小一片**：

| 能力 | 本项目 |
|---|---|
| 读取屏幕内容 | ❌ `canRetrieveWindowContent=false` |
| 模拟点击 / 手势 | ❌ 未声明 `canPerformGestures`，代码中不存在 `dispatchGesture` / `performAction` |
| 读取输入文本 | ❌ 只监听 `typeWindowStateChanged`，不监听文本事件 |
| 获知"哪个应用被打开" | ✅ 仅此一项 |

拿到包名后立即交给 `AutoResponder`，处置一律通过 Shizuku 命令执行，
而不是在界面上"点"——这与滥用无障碍权限模拟点击的常见做法刻意相反。

### 9.7 安全设计（刻意保守）

- **自动处置默认关闭**：`GuardPolicy.autoRespond` 默认为 `false`，
  默认状态下本应用只提醒、不处置；
- **未授权 Shizuku 时无法开启自动终止**，界面直接拦下并指路；
- 守护模式（常驻盯梢）与自动处置（盯到后动手）是**两个独立开关**，刻意不合并；
- 存储损坏时回退保守默认值，绝不因读取失败而意外开启自动处置。
